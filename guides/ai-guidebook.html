AI Game Guidebook

How we build Roblox games with AI agents: what the AI can do on its own, how it checks its own work, and what still needs a human yes. Written from what happened on Steal a Slime, PRs #1 to #655.

01

House rules

These hold for every game, every bot and every task. The first three are about who decides; the rest keep the game and the PC safe.

  1. A human signs off everything players see or hear. 3D models, UI screens, world placement, music, sound effects and player-facing wording are reviewed by Merijn or Niels before they ship.

    An AI review, a bot reviewer or a playtest subagent "Pass" is evidence, not a sign-off.

  2. Show it before you build it. Anything visible starts as a mockup, render or before/after page with options. The human picks; the PR quotes the pick.

    See chapter 02. Every approved UI change on Steal a Slime went this way.

  3. Nothing goes out without Merijn's OK. No Published upload, no asset upload or re-upload, no merge to main by a bot.

    Uploading before approval left an unused wind loop on the account (#380).

  4. Never touch production DataStores. Tests and cloud scripts run with DataStoreMode = "Memory". Cheats only go through the guarded test hooks.
  5. The AI never plays on a real Roblox account. Testing happens in Studio over MCP or in Open Cloud Luau Execution. Driving the real client risks a ban that can reach the account that owns the game.
  6. Don't interrupt the person at the PC. Studio runs on a hidden desktop, muted. No real mouse or keyboard input. Close only the Studio you opened.
  7. Report what you did not check. Every PR lists the checks it ran and the ones it could not. Missing evidence counts as a fail, and "not listened to by ear" or "not tested on phone" is said out loud.
  8. One task, one worktree, one branch. Cut from a freshly pulled main, stage your own files by path, never commit to main.
  9. One place for every value. Colours in the palette file, sizes in Layout, tunables in Config, world sizes in WorldLayout. Never copy a number into a second file.
  10. Common systems live in shared, not in a game. Inventory and hotbar, session-locked saves, save migrations, rate limiting, number formatting, seeded random and analytics are in shared/luau. Before building one of these, use or extend the shared module. When something you built in a game has nothing game-specific in it, move it to shared.

    Shared modules are a pure core plus a thin Roblox adapter, take their dependencies as arguments, ship overridable defaults (like the default hotbar UI) and have Lune specs. See shared/luau/CLAUDE.md.

  11. No secrets in output. The Open Cloud key is never printed or committed.
02

From idea to merge

Two routes, picked by size. Both end with a human choosing between concrete options, not reading a description.

  1. Write a brief. Goal, a checkable finish line, evidence, scope, what is forbidden, a timebox. A brief without a goal or finish line is sent back. (guides/task-brief.md)
  2. Big feature: an HTML proposal in docs/. The page lays out the options and ends in a "Decided" section with Merijn's answers. Economy, merge vat, rebirth, obby and admin menu all went this way. #561 #535 #600 #652 #620
  3. Small or visual change: a claude.ai artifact. Now vs option A, B, C, or an audit with before/after pictures. Merijn picks; the PR quotes the pick. #593 #613 #617 #651
  4. Build in a worktree, with the game's checks green: tests, lint, format, typecheck, place safety, layout gate.
  5. Check it in the real engine (chapter 08) and put the screenshots and numbers in the PR body.
  6. Human review and merge. The bot answers every PR comment with the commit and the tests it ran. Merijn merges.
Worked

Mockup first was the common factor of every UI change that was approved without a second round. Changes shipped without a Studio or phone check (#316 #348 #458) were the ones that came back.

03

Start every game with a kit

Before the first real screen, build the game's kit: one palette, two fonts, a small set of UI parts, a size table and a written style guide. On Steal a Slime it is the GooKit. Once it existed, one change to the kit restyled every menu at once (#448), and bots stopped inventing their own buttons.

Name it after the game's look (<Look>Kit) and build it in five steps, as GooKit did: kit, HUD, copy and empty states, world labels and loading screen, clean-up plus the style guide #448 #454 #485 #491 #506.

What goes in a kit

Palette file

Every colour once, as RGB, read by the HUD, world signs and props. GooKit: shared/GooPalette.luau.

Two fonts

A display face for titles, buttons and numbers (Fredoka One), a body face for sentences (Nunito Bold).

UI parts

Panel with header band and X, button, hold-to-confirm button, status well, chip, row, check mark, notice ring, scroll list. GooKit: src/ui/Widgets.luau.

Size table

Touch targets at least 44 px, text at least 14 px, panel chrome, draw order, and phone, landscape-phone and narrow modes. src/ui/Layout.luau.

Style guide

Which colour means what, which button where, how to write. Decided by Merijn, kept in UI-STYLEGUIDE.md.

Gates

Specs that fail on a broken kit, a layout check at six screen sizes and an instance budget that only ratchets down.

Colour has one job

ColourMeansNever use it for
GoldMoney, collecting a rewardDecoration, headings
Mint (accent)The main action, income, progressSecondary buttons
Pink (bad)Losing something: stolen, sell, deleteClose buttons on harmless menus
Info tealSecondary actionsThe main action
Warn amberTimers and cooldownsErrors

Gates that keep the kit honest

  • Layout gate at 390×844, 844×390, 768×1024, 1024×768, 1366×768 and 1920×1080, each also minus the 58 px Roblox top bar: on screen, touch size, no overlaps, text fits, nav reachable.
  • Kit specs: one shared goo edge per screen, fonts and emoji used in the right places, panel padding the same everywhere.
  • Instance budget (ui-perf-budget.json): going over fails, and so does coming in under until the limit is lowered. It forced shared parts and saved about 830 instances in #448.

Sources: games/steal-a-slime/UI-STYLEGUIDE.md, src/ui/Widgets.luau, src/ui/Layout.luau, tests/ui/GooKit.spec.luau, tests/ui/LayoutAssert.luau.

04

Making UIs

The AI builds every screen from kit parts, in code, and checks it at real phone sizes. The hard part is not drawing the screen; it is keeping it simple. Most rework was about too much on screen, not about bugs.

How the AI does it

  1. Mockup with options as an artifact or HTML page, at phone size first.
  2. Build from kit parts only. No raw Frames, no raw colours, no raw ZIndex numbers.
  3. Run the layout gate at all six sizes and the kit specs.
  4. Screenshot in a muted hidden Studio on phone and PC sizes, and put the shots in the PR.
  5. Human picks and reviews (Merijn or Niels).

Approved

  • One status pill per moment: the boss card went from three lines to two #490
  • Say why instead of a dead prompt: "Need $39.9K more", or why a slime can't be grabbed #485 #543
  • Tabs and a side pane instead of one long list: SlimeDex, Skins, Settings #552 #562 #626
  • One card instead of a stack: the thieves card folds into the boss card #631
  • One padding value for every card #638
  • A drawn check mark instead of an emoji #642

Needed rework

  • Too busy: boss card plus steal cards crowding the top #631; landscape-phone HUD #556; top bar and toasts removed #316
  • Too many options: the merge vat picker with filters, Pick for me and Auto-merge lost to "move slimes in, three slots" #348 → #535
  • Wrong size on phone: X and padlock "way too big" #653; unreadable slime tags #556 #623; jump button overlap #458
  • Unclear wording: "Rebirth 4" read as your current rebirth; now "Next rebirth: 4" #651
  • Covering menus: banners, arrows and the boss card drawn over open menus #137 #143 #516
  • Placement churn: the tutorial card moved three times #611 #629

Writing on screen

  • Fewer words beat smaller words. A hint that would need text under 14 px is cut, not shrunk.
  • Sentence case. ALL CAPS only for alarms ("STOLEN!", "BOSS INCOMING"). No "!" on buttons.
  • One main button per card. Anything you can't undo is hold-to-confirm.
  • A disabled button says what is missing. Every list has an empty state.
  • Nothing new goes on the HUD without a slot in the size table. Notices never cover a menu's X or the hotbar.
05

3D models: create, verify, iterate

The AI cannot use Blender's viewport, so every model is a Python script that headless Blender turns into a mesh, a picture sheet and numbers. The AI looks at the sheet, changes one or two things and runs again. All of it lives in shared/modeling-kit.

The loop

  1. Read LESSONS.md and look at how the game uses the mesh: its slot, size, what covers it, whether the game tints it.
  2. Write the model as code: models/<name>.py from boxes, tubes, lathes and metaballs. 1 unit = 1 stud, Z up, front faces −Y, standing on z=0. Colour is vertex colour only.
  3. Render a round: python iterate.py models/<name>.py --sheet sheets/<name>_rNN.png. Four views beside a 5-stud avatar block, plus stats.json. About 3 seconds.
  4. Look at the sheet, not just the numbers. Critique in a fixed order: silhouette, proportions, scale against the avatar, colour, triangles. Log the round.
  5. Repeat, then stop after about six rounds. If it still isn't good, say so instead of shipping a weak model.
  6. Final look with --look roblox --turntable, then a human review of the sheet.
  7. Upload with Merijn's OK (upload.py --go; dry run by default), then check it in a Studio playtest from the front, at an angle and from behind.

What the checks catch

CheckFailsWarns
Triangles10,000+ per meshOutside 500–2,000 for a prop
SizeOver 2,048 studs on any axisScript asserts: seat height, fits its box, grip point
FileFBX 20 MB or moreMore than one mesh or material, textures, missing vertex colour
GeometryNon-manifold edges

Approved

  • Slime Ranch theme, after Volcanic Meadow was dropped the day it was locked #5 → #7
  • A shop cabinet showing the six upgrades #422
  • The jar base, picked from rendered concepts over a tree and islands #400
  • The Exclusive shop as a fair tent, then a carousel
  • Metaballs for goo, drips and blobs

Needed rework

  • Off-theme ideas: gear tower, mushroom hut, gym barn, silo and windmill shops; purple-and-gold "epic" shop concepts
  • Colours: cream on big surfaces and cold metal; darks that went muddy in Roblox light (red to maroon, butter to olive)
  • Scale: the first kit oak was 10–45% too big; parts under ~0.5 stud vanish at game distance
  • Only visible in game: flickering faces from decals too close together, 77 slimes re-uploaded #601; a title strip showing through a sign #619
  • Unplaced: 39 of 58 uploaded models had no world slot

Lessons worth copying

  • Match the size of the mesh you replace within 10%. Render the old one first.
  • Start dark colours at a value of 115 or more and lift them 15–20%. Roblox light crushes darks.
  • MeshPart.Color multiplies vertex colours, so a mesh the game tints is modelled in greys.
  • Spend triangles on the silhouette. Bevels on hidden faces took a windmill from 3,372 to 1,970 with no visible loss.
  • Overlapping closed parts beat booleans: no broken edges, exact colours per part.
  • Check axes on the exported file or in Studio, never on the sheet. Kit −Y becomes Roblox +Z.
06

World placement

The map is code: WorldLayout.luau describes every node, a script generates the world files, and tests fail when they are stale. Studio edits are lost on the next build. Most world bugs were found by walking around, so the guides below come from measuring, not from looking at renders.

Worked well

  • The world as one data tree, with every value in one place; Lune can check it without Studio
  • Invisible collider slots with kit meshes swapped in
  • A terrain burial probe on a real server before every publish, 0.25-stud threshold #309
  • An explicit collision choice per prop, enforced by a test
  • An audit page with before/after pictures, approved fix by fix #617

Did not

  • Sinking: terrain rendered 2 studs high and buried plots, the fountain and spawn #308
  • Invisible walls: hulls around open shapes, 16 studs beside the windmill, 4–7 out from tree tops
  • Glass material: Roblox draws nothing see-through behind it, so slimes and signs vanished #541 #549
  • Labels: a label floating across the map 140 studs away #615; stacked tags #599; a slime covering its own tag #437
  • Standing inside things: players inside a base's drop tube #617

Placement rules

  • The visible floor never collides; terrain is the walk surface. One height constant for the floor.
  • Choose collision before upload; it is fixed at import. Use precise collision for open shapes, a post for a tree trunk.
  • No Glass material anywhere. A test bans it.
  • Every floor of every base shows its slimes from outside: glass bands on each floor, nothing covering them.
  • Keep walkways wide enough to walk: 2.5 studs between jar stands.
  • World labels follow guides/roblox-world-labels.md: plan for a phone, at least 14 px on screen, an explicit MaxDistance, and a row in the label registry in the same PR.
07

Music and sound

The AI cannot hear. It can measure, log and pick by name and length; the taste call is always human. There are two ways to get a sound, both in or next to shared/audio-kit.

RouteHowBest for
SynthesisedA Python recipe renders a repeatable .ogg plus a waveform and spectrogram sheet. Checks: onset under 5 ms, peak −1 dBFS, mono 44.1 kHz, loudness stored per sound.UI clicks, pops, cash, short game cues
Roblox libraryFree public-domain music and effects by asset id, checked as public domain and as loading in Studio.Music, ambience, animals, nature

Approved

  • The music pass with 22 synth sounds #564
  • Birds at night; a real owl as random one-shots every 20–45 s #380
  • Small random pitch on frequent sounds; a test that bans two sounds sharing one id #605

Rejected

  • Crickets (annoying), synth wind and synth owls #380
  • Odd first picks: a finger snap for cash, a 6 s rocket for unlock, a sword slash for escape #564
  • Sounds for Rare and Secret drops: they stay silent #381
Test silently

A hidden Studio still plays through the speakers. Right after starting a playtest, set every Sound and SoundGroup volume to 0 and keep doing it for new ones. Check audio by logging which sounds were created and played.

Verifying in the real game

Tests prove logic; only the engine proves how it looks and feels. Every visible change gets at least one layer from the engine side.

LayerWhat it provesWhen
Lune tests and boot testLogic, saves, that the game startsEvery commit
Static layout and render checkUI fits at six sizes; part and triangle budgetsEvery PR
Hidden Studio over MCPScreenshots, collisions, labels, timings, a 2-player testEvery visible change
Cloud Luau ExecutionBehaviour on a real server: terrain probe, smoke testBefore publish
Human reviewLooks right, feels right, reads rightBefore merge
Players and analyticsWhether it helps the funnelAfter release

Tips

  • Screenshots leave out BillboardGuis. Read label sizes with execute_luau (AbsoluteSize, WorldToViewportPoint).
  • Measure, then state the number: "label shows at 54 studs, hidden at 66" #615.
  • Walk a dummy into props from four sides to find invisible walls.
  • Drive input with Studio-only attributes, never the real mouse.
  • The PR body lists exact checks and results, and says plainly what was not tested.

New game checklist

What a bot sets up in the first days of a new game, so game two starts where Steal a Slime ended instead of where it began. Each step is something we had to add later on Steal a Slime, often after it went wrong.

Before any code

  1. Pitch page. An HTML proposal with the core loop, the first five minutes of play and what makes it fun. Merijn answers in a "Decided" section.
  2. Theme from renders. Render two or three looks on a few key props and pick one before modelling everything. Volcanic Meadow was locked and dropped on the same day, after 21 meshes were already recoloured #5 → #7.
  3. Write the theme sheet. Palette, materials, what is banned (on Steal a Slime: cream on big surfaces, cold metal). It goes in shared/modeling-kit/THEME.md or the game's own theme file.

First commit: repo and gates

  1. Folder and rules. games/<name>/ with its own CLAUDE.md. Copy the hard rules from Steal a Slime: Memory DataStore, no Published upload, no secrets, ownership, no history in code.
  2. Toolchain. rokit.toml (Rojo, Lune, selene, stylua, luau-lsp), a test runner, check-place, typecheck.sh, and a CI workflow that runs them on every PR.
  3. Safety switches. DataStoreMode = "Memory" for tests, a TestHooks module with the guard and its spec, upload scripts that dry-run by default.
  4. Budgets file. Part, triangle, mesh-slot and UI instance limits in one budgets.json. Raising one needs Merijn's OK and a reason #652.

First playable: shared systems and kit

  1. Mount shared/luau as ReplicatedStorage.Lib and use what is there before writing anything: saves with session lock and migrations, inventory and hotbar, rate limiter, number format, settings, receipt ledger, guide arrows, label fitting.
  2. Analytics from day one. The shared tracker with an onboarding funnel and a shop funnel. Without it, the first release gives you no numbers to plan from.
  3. The kit (Guides, chapter 03): palette file, two fonts, UI parts, size table, style guide, layout gate at six sizes, instance budget. Before the first real screen.
  4. World as data. A WorldLayout tree, generated world files with a "stale" spec, one floor height constant, a collision choice per prop and a world label registry.
  5. Hidden Studio check. Make sure a bot can open the place with studio_hidden.py, mute it and take screenshots, before the first visual PR.

Copy, or make new?

Copy from Steal a SlimeMake new for each game
Hard rules in CLAUDE.md, code structure (ctx, entry scripts only wire)Theme, palette and fonts
Test harness, layout gate, perf budget spec, place safety checkThe kit's parts and style guide

Rule of thumb

If a step above is missing when the first feature PR opens, that PR adds it first. Adding gates later means fixing everything that slipped through before them, as with the label sizes on Steal a Slime #623.

Briefs and prompts

A good brief saves a review round. A bot rejects a brief without a goal or a checkable finish line, and asks for a better one before it starts.

The task brief

FieldWhat to write
GoalThe outcome, in one sentence
FinishA condition that is true or false. Not "looks good".
EvidenceWhat the report shows: screenshots, numbers, test output, commit
ScopeThe paths and branch the bot may touch
VerifyThe exact commands or Studio checks that prove it works
ForbiddenWhat the bot must not do
TimeboxMaximum time or rounds, and what to do when it runs out

Good brief

  • Goal: the Ritual label stops showing across the map.
  • Finish: hidden past 60 studs (40 on phone), measured in Studio.
  • Evidence: before/after shots, the measured show/hide distances.
  • Scope: the label's view module and the label registry.
  • Forbidden: fading, other labels, uploads.
  • Timebox: one PR; report if Studio can't measure it.

Weak brief

  • "Make the labels better."
  • No finish line, so the bot decides when it's done.
  • No scope, so it restyles every label at once.
  • No evidence asked, so the PR says "looks good".

Prompt starters

ForStart with
A big feature"Write an HTML proposal in docs/ for X: the problem, two or three options with pictures, your recommendation, and a Decided section I fill in. Don't build yet."
A screen"Make a mockup page with the current screen and options A, B and C at phone size, built from the kit. Fewest words wins."
A 3D model"Model X with the modeling kit. Match the old mesh's size within 10%. Six rounds at most; if it isn't good by then, show me the best round and say what limits it."
A sound"Find three free library options for X, or synthesise one with the audio kit. Give ids, lengths and measurements. Don't upload."
A world problem"Audit X in a hidden Studio: walk into it from four sides, measure, and make a page with before/after pictures and one fix per problem for me to approve."
A bug"Reproduce X, write a test that fails because of it, then fix it. Show the failing and passing output."

What a PR body must show

ChangeEvidence
3D modelFinal sheet, round log, triangle count, in-game shots from the front, at an angle and from behind
UIPhone and PC screenshots, layout gate result, the option Merijn picked
SoundAsset ids, measurements, which sounds were logged as played, and "not listened to by ear"
WorldMeasured distances, collision walk test, burial probe if anything touches the ground
LogicThe test that failed before the fix, the checks run, what was not tested

Feedback that sticks

  • Pick from options ("option A"), and the PR quotes your words. Bots follow quotes better than summaries.
  • When you decide something for good, ask the bot to add it to the Decision log tab, so the next bot doesn't propose it again.
  • Say what you don't want as well: "no Coming soon placeholders" saved a later round on the cloud skins.

Economy and data

The AI can't feel pacing, but it can run hundreds of simulated players on the real game code and read the funnels. Balance before release with the sim; decide what to build next from analytics.

The loop

  1. Simulate. Run the pacing sim on the real game code and compare before and after.
  2. Ship with the analytics events in place.
  3. Wait for data: at least 7 days or 1,000 players in the first step, whichever comes later.
  4. Find the biggest drop between two funnel steps. That is the next target, with at most one second target.
  5. Write the goal as step, from, to, by when. For example: "first slime to first sale, from 41% to 55%, within 7 days of release."
  6. Only then look at ideas, including competitors'. "Steal a Brainrot has it" is not a reason.

Pacing sim

Bots play the real World, GameLoop and Actions code under Lune. Profiles: casual, average, grinder, casual15, thief, victim. Results are medians with 10–90% ranges. Code in tools/livetest/pacing; a spec keeps it working.

lune run tools/livetest/pacing --seeds 1-20 --days 7
lune run tools/livetest/pacing --seeds 1-4 --days 55 --mix average=5,grinder=5,casual=6

Analytics rules

  • Send events from the server only. Roblox drops client events and everything from Studio.
  • Use the shared tracker (shared/luau/src/analytics). It keeps names to a catalog and stays at 80% of Roblox's rate limit, batching frequent events per minute.
  • Never rename or renumber a funnel step after it ships; it breaks the comparison with older versions.
  • One currency with fewer than 20 transaction types. Roblox lumps the rest into "Other"; a spec checks the count.
  • Read numbers from the Creator Dashboard on a published version, never from a Studio session.

A roadmap item needs all four

  • A measurable goal: a number, a direction and a time window.
  • The event that measures it: funnel, step number, step name.
  • The baseline from the current live version.
  • Proof the event is logged on the server: file and line.

Anything missing one of these goes on the parked list. Park it as well if it targets a step that already converts well, adds a parallel system where an existing one could grow, or needs paid random rewards.

Release

Bots build, test and prepare a release on their own. Players only get it after Merijn approves it at the 12:00 or 19:00 release check. Auto-publish is off.

From merge to live

  1. Merge to main by Merijn, after review.
  2. Cloud tests. A test build runs on a real Roblox server. That build is never promoted.
  3. Full Studio report. A hidden Studio run takes frames on every device size. A named reviewer marks the frames reviewed. Partial runs never count.
  4. Gate. Cloud tests pass, the full report passes and is newer than the merge. Only the newest fully gated commit goes out; older ones are skipped.
  5. Clean build without test code, uploaded as a Saved version.
  6. Smoke test and terrain probe on that exact Saved version. A failure stops the release.
  7. Merijn's OK at the release check.
  8. Published upload of the same file, then the probe again on the live version.
  9. First hour: watch errors and funnels, and send a short release note to SuperBottie.

First hour after a release

  • Errors: the Creator Dashboard error report and server console. Re-run the release check on the live version.
  • Funnels: compare each onboarding and shop step with the previous version.
  • A clear drop or a new error means roll back.

Rolling back

  1. Write down what is live before every publish, so you know what to go back to.
  2. Re-upload the previous file as Published (it becomes a new version with the old content), or restore it in Creator Hub's version history.
  3. Check it with the release check, and tell SuperBottie what was rolled back and why.
SituationWhat the bot does
Upload returns 409 "Server is busy"Retry after 1, 2, 4 and 8 minutes, then stop and report
Studio report missing or partialWait; the commit is not released
Smoke test or terrain probe failsStop; nothing is published
Something is published by mistakeRoll back first, explain after
Never

Upload Published without Merijn's OK, ship a place that sets DataStoreMode, or print the Open Cloud key. A place-safety check and a spec fail the build if DataStoreMode is set.

Adding a decision

One row per decision: area, what was decided in a few words, why, and the PR or proposal. A bot adds the row in the same PR that carries the decision out.

Glossary

Our own words, for a new person or a new bot.

Team

Merijn
Owner. Approves visuals, sounds, uploads and releases, and merges PRs.
Niels
Co-reviewer. Signs off models, UI and other visible work alongside Merijn.
Phoenix
Bot that owns server, shared code, the world and scripts.
Jolt
Bot that owns the UI (src/ui, tests/ui).
Archer
Bot that owns src/visuals.
Gojo
Bot for planning from funnel data and for critical review.
SuperBottie
Coordinator bot: checks proposals, gets release notes, asks "is this already built?".

Tools

Rojo
Builds the place file from the files in the repo. The repo is the source of truth; Studio edits are lost.
Lune
Runs Luau outside Roblox. Used for tests, world generation and the pacing sim.
rokit
Installs the pinned toolchain versions from rokit.toml.
selene, stylua, luau-lsp
Linter, formatter and type checker.
Studio MCP
Lets a bot read the game tree, run Luau, start playtests and take screenshots in Studio.
Hidden Studio
Studio opened on a hidden desktop with studio_hidden.py, so bots never disturb the person at the PC.
pc-watcher
Runs Studio checks for each commit on main and writes the Studio report.
pr-gate
Fast checks on a PR: logic tests, layout at five sizes, budgets, types.
rhr
Headless renderer for a quick static check. Draws unknown meshes as boxes, so it is not proof of looks.
Open Cloud
Roblox's web API for uploading places and assets and running Luau on a real server (Luau Execution).
Modeling kit
shared/modeling-kit: Blender models as Python scripts, rendered and checked headless.
Audio kit
shared/audio-kit: synthesised sounds as Python recipes, with measured checks.
shared/luau
Game-agnostic Luau systems every game reuses: saves, inventory, analytics and more.

Words we use

Kit (GooKit)
A game's UI building blocks: palette, fonts, parts, sizes and style guide. GooKit is Steal a Slime's.
GooPalette
The one file that holds every Steal a Slime colour.
Contact sheet
The four-view picture the modeling kit renders each round, with an avatar block for scale.
Round
One pass of change, render and critique on a model. About six is the limit.
Roblox look
--look roblox: a render with game-like lighting. Close, but not calibrated against Studio.
Slot
An invisible collider part in the world that a kit mesh is swapped onto.
Collision fidelity
How a mesh collides (Box, Hull, Default, Precise). Fixed at import, so pick it before uploading.
Saved / Published
A Saved version is uploaded but not live. Published is what players get, and needs Merijn's OK.
Memory mode
DataStoreMode = "Memory": saves stay in memory, so tests never touch real player data.
TestHooks
The one guarded place for cheats (cash, time, slimes). Only works in Memory mode.
Contract
CONTRACT.md and contract/*.md: shared names and rules, written before the code.
WorldLayout
The data tree that describes the whole map.
Label registry
The list of every world label with its size kind and view distance, in the world labels guide.
Layout gate
Test that checks every screen at six sizes for overlaps, touch size and text fit.
Budget ratchet
A limit that fails when you go over and also when you come in under, until the limit is lowered.
Pacing sim
Simulated players on the real game code to check how fast progress goes.
Funnel
A list of steps players go through (onboarding, shop). The biggest drop between steps is what to fix.
Terrain probe
A check on a real server that nothing is buried in the ground before and after a release.
Studio report
Frames and results from a full hidden Studio run for one commit, reviewed by name.
Fully gated
A commit with passing cloud tests and a reviewed, passing full Studio report. Only the newest one releases.
Worktree
A separate folder and branch per task, so bots don't switch each other's checkout.
ctx
The one way to pass engine access and test overrides into a module.
