01

House rules

These hold for every game, every bot and every task. The first three are about who decides; the rest keep the game and the PC safe.

  1. A human signs off everything players see or hear. 3D models, UI screens, world placement, music, sound effects and player-facing wording are reviewed by Merijn or Niels before they ship.

    An AI review, a bot reviewer or a playtest subagent "Pass" is evidence, not a sign-off.

  2. Show it before you build it. Anything visible starts as a mockup, render or before/after page with options. The human picks; the PR quotes the pick.

    See chapter 02. Every approved UI change on Steal a Slime went this way.

  3. Nothing goes out without Merijn's OK. No Published upload, no asset upload or re-upload, no merge to main by a bot.

    Uploading before approval left an unused wind loop on the account (#380).

  4. Never touch production DataStores. Tests and cloud scripts run with DataStoreMode = "Memory". Cheats only go through the guarded test hooks.
  5. The AI never plays on a real Roblox account. Testing happens in Studio over MCP or in Open Cloud Luau Execution. Driving the real client risks a ban that can reach the account that owns the game.
  6. Don't interrupt the person at the PC. Studio runs on a hidden desktop, muted. No real mouse or keyboard input. Close only the Studio you opened.
  7. Report what you did not check. Every PR lists the checks it ran and the ones it could not. Missing evidence counts as a fail, and "not listened to by ear" or "not tested on phone" is said out loud.
  8. One task, one worktree, one branch. Cut from a freshly pulled main, stage your own files by path, never commit to main.
  9. One place for every value. Colours in the palette file, sizes in Layout, tunables in Config, world sizes in WorldLayout. Never copy a number into a second file.
  10. No secrets in output. The Open Cloud key is never printed or committed.
02

From idea to merge

Two routes, picked by size. Both end with a human choosing between concrete options, not reading a description.

  1. Write a brief. Goal, a checkable finish line, evidence, scope, what is forbidden, a timebox. A brief without a goal or finish line is sent back. (guides/task-brief.md)
  2. Big feature: an HTML proposal in docs/. The page lays out the options and ends in a "Decided" section with Merijn's answers. Economy, merge vat, rebirth, obby and admin menu all went this way. #561 #535 #600 #652 #620
  3. Small or visual change: a claude.ai artifact. Now vs option A, B, C, or an audit with before/after pictures. Merijn picks; the PR quotes the pick. #593 #613 #617 #651
  4. Build in a worktree, with the game's checks green: tests, lint, format, typecheck, place safety, layout gate.
  5. Check it in the real engine (chapter 08) and put the screenshots and numbers in the PR body.
  6. Human review and merge. The bot answers every PR comment with the commit and the tests it ran. Merijn merges.
Worked

Mockup first was the common factor of every UI change that was approved without a second round. Changes shipped without a Studio or phone check (#316 #348 #458) were the ones that came back.

03

Start every game with a kit

Before the first real screen, build the game's kit: one palette, two fonts, a small set of UI parts, a size table and a written style guide. On Steal a Slime it is the GooKit. Once it existed, one change to the kit restyled every menu at once (#448), and bots stopped inventing their own buttons.

Name it after the game's look (<Look>Kit) and build it in five steps, as GooKit did: kit, HUD, copy and empty states, world labels and loading screen, clean-up plus the style guide #448 #454 #485 #491 #506.

What goes in a kit

Palette file

Every colour once, as RGB, read by the HUD, world signs and props. GooKit: shared/GooPalette.luau.

Two fonts

A display face for titles, buttons and numbers (Fredoka One), a body face for sentences (Nunito Bold).

UI parts

Panel with header band and X, button, hold-to-confirm button, status well, chip, row, check mark, notice ring, scroll list. GooKit: src/ui/Widgets.luau.

Size table

Touch targets at least 44 px, text at least 14 px, panel chrome, draw order, and phone, landscape-phone and narrow modes. src/ui/Layout.luau.

Style guide

Which colour means what, which button where, how to write. Decided by Merijn, kept in UI-STYLEGUIDE.md.

Gates

Specs that fail on a broken kit, a layout check at six screen sizes and an instance budget that only ratchets down.

Colour has one job

ColourMeansNever use it for
GoldMoney, collecting a rewardDecoration, headings
Mint (accent)The main action, income, progressSecondary buttons
Pink (bad)Losing something: stolen, sell, deleteClose buttons on harmless menus
Info tealSecondary actionsThe main action
Warn amberTimers and cooldownsErrors

Gates that keep the kit honest

  • Layout gate at 390×844, 844×390, 768×1024, 1024×768, 1366×768 and 1920×1080, each also minus the 58 px Roblox top bar: on screen, touch size, no overlaps, text fits, nav reachable.
  • Kit specs: one shared goo edge per screen, fonts and emoji used in the right places, panel padding the same everywhere.
  • Instance budget (ui-perf-budget.json): going over fails, and so does coming in under until the limit is lowered. It forced shared parts and saved about 830 instances in #448.

Sources: games/steal-a-slime/UI-STYLEGUIDE.md, src/ui/Widgets.luau, src/ui/Layout.luau, tests/ui/GooKit.spec.luau, tests/ui/LayoutAssert.luau.

04

Making UIs

The AI builds every screen from kit parts, in code, and checks it at real phone sizes. The hard part is not drawing the screen; it is keeping it simple. Most rework was about too much on screen, not about bugs.

How the AI does it

  1. Mockup with options as an artifact or HTML page, at phone size first.
  2. Build from kit parts only. No raw Frames, no raw colours, no raw ZIndex numbers.
  3. Run the layout gate at all six sizes and the kit specs.
  4. Screenshot in a muted hidden Studio on phone and PC sizes, and put the shots in the PR.
  5. Human picks and reviews (Merijn or Niels).

Approved

  • One status pill per moment: the boss card went from three lines to two #490
  • Say why instead of a dead prompt: "Need $39.9K more", or why a slime can't be grabbed #485 #543
  • Tabs and a side pane instead of one long list: SlimeDex, Skins, Settings #552 #562 #626
  • One card instead of a stack: the thieves card folds into the boss card #631
  • One padding value for every card #638
  • A drawn check mark instead of an emoji #642

Needed rework

  • Too busy: boss card plus steal cards crowding the top #631; landscape-phone HUD #556; top bar and toasts removed #316
  • Too many options: the merge vat picker with filters, Pick for me and Auto-merge lost to "move slimes in, three slots" #348 → #535
  • Wrong size on phone: X and padlock "way too big" #653; unreadable slime tags #556 #623; jump button overlap #458
  • Unclear wording: "Rebirth 4" read as your current rebirth; now "Next rebirth: 4" #651
  • Covering menus: banners, arrows and the boss card drawn over open menus #137 #143 #516
  • Placement churn: the tutorial card moved three times #611 #629

Writing on screen

  • Fewer words beat smaller words. A hint that would need text under 14 px is cut, not shrunk.
  • Sentence case. ALL CAPS only for alarms ("STOLEN!", "BOSS INCOMING"). No "!" on buttons.
  • One main button per card. Anything you can't undo is hold-to-confirm.
  • A disabled button says what is missing. Every list has an empty state.
  • Nothing new goes on the HUD without a slot in the size table. Notices never cover a menu's X or the hotbar.
05

3D models: create, verify, iterate

The AI cannot use Blender's viewport, so every model is a Python script that headless Blender turns into a mesh, a picture sheet and numbers. The AI looks at the sheet, changes one or two things and runs again. All of it lives in shared/modeling-kit.

The loop

  1. Read LESSONS.md and look at how the game uses the mesh: its slot, size, what covers it, whether the game tints it.
  2. Write the model as code: models/<name>.py from boxes, tubes, lathes and metaballs. 1 unit = 1 stud, Z up, front faces −Y, standing on z=0. Colour is vertex colour only.
  3. Render a round: python iterate.py models/<name>.py --sheet sheets/<name>_rNN.png. Four views beside a 5-stud avatar block, plus stats.json. About 3 seconds.
  4. Look at the sheet, not just the numbers. Critique in a fixed order: silhouette, proportions, scale against the avatar, colour, triangles. Log the round.
  5. Repeat, then stop after about six rounds. If it still isn't good, say so instead of shipping a weak model.
  6. Final look with --look roblox --turntable, then a human review of the sheet.
  7. Upload with Merijn's OK (upload.py --go; dry run by default), then check it in a Studio playtest from the front, at an angle and from behind.

What the checks catch

CheckFailsWarns
Triangles10,000+ per meshOutside 500–2,000 for a prop
SizeOver 2,048 studs on any axisScript asserts: seat height, fits its box, grip point
FileFBX 20 MB or moreMore than one mesh or material, textures, missing vertex colour
GeometryNon-manifold edges

Approved

  • Slime Ranch theme, after Volcanic Meadow was dropped the day it was locked #5 → #7
  • A shop cabinet showing the six upgrades #422
  • The jar base, picked from rendered concepts over a tree and islands #400
  • The Exclusive shop as a fair tent, then a carousel
  • Metaballs for goo, drips and blobs

Needed rework

  • Off-theme ideas: gear tower, mushroom hut, gym barn, silo and windmill shops; purple-and-gold "epic" shop concepts
  • Colours: cream on big surfaces and cold metal; darks that went muddy in Roblox light (red to maroon, butter to olive)
  • Scale: the first kit oak was 10–45% too big; parts under ~0.5 stud vanish at game distance
  • Only visible in game: flickering faces from decals too close together, 77 slimes re-uploaded #601; a title strip showing through a sign #619
  • Unplaced: 39 of 58 uploaded models had no world slot

Lessons worth copying

  • Match the size of the mesh you replace within 10%. Render the old one first.
  • Start dark colours at a value of 115 or more and lift them 15–20%. Roblox light crushes darks.
  • MeshPart.Color multiplies vertex colours, so a mesh the game tints is modelled in greys.
  • Spend triangles on the silhouette. Bevels on hidden faces took a windmill from 3,372 to 1,970 with no visible loss.
  • Overlapping closed parts beat booleans: no broken edges, exact colours per part.
  • Check axes on the exported file or in Studio, never on the sheet. Kit −Y becomes Roblox +Z.
06

World placement

The map is code: WorldLayout.luau describes every node, a script generates the world files, and tests fail when they are stale. Studio edits are lost on the next build. Most world bugs were found by walking around, so the guides below come from measuring, not from looking at renders.

Worked well

  • The world as one data tree, with every value in one place; Lune can check it without Studio
  • Invisible collider slots with kit meshes swapped in
  • A terrain burial probe on a real server before every publish, 0.25-stud threshold #309
  • An explicit collision choice per prop, enforced by a test
  • An audit page with before/after pictures, approved fix by fix #617

Did not

  • Sinking: terrain rendered 2 studs high and buried plots, the fountain and spawn #308
  • Invisible walls: hulls around open shapes, 16 studs beside the windmill, 4–7 out from tree tops
  • Glass material: Roblox draws nothing see-through behind it, so slimes and signs vanished #541 #549
  • Labels: a label floating across the map 140 studs away #615; stacked tags #599; a slime covering its own tag #437
  • Standing inside things: players inside a base's drop tube #617

Placement rules

  • The visible floor never collides; terrain is the walk surface. One height constant for the floor.
  • Choose collision before upload; it is fixed at import. Use precise collision for open shapes, a post for a tree trunk.
  • No Glass material anywhere. A test bans it.
  • Every floor of every base shows its slimes from outside: glass bands on each floor, nothing covering them.
  • Keep walkways wide enough to walk: 2.5 studs between jar stands.
  • World labels follow guides/roblox-world-labels.md: plan for a phone, at least 14 px on screen, an explicit MaxDistance, and a row in the label registry in the same PR.
07

Music and sound

The AI cannot hear. It can measure, log and pick by name and length; the taste call is always human. There are two ways to get a sound, both in or next to shared/audio-kit.

RouteHowBest for
SynthesisedA Python recipe renders a repeatable .ogg plus a waveform and spectrogram sheet. Checks: onset under 5 ms, peak −1 dBFS, mono 44.1 kHz, loudness stored per sound.UI clicks, pops, cash, short game cues
Roblox libraryFree public-domain music and effects by asset id, checked as public domain and as loading in Studio.Music, ambience, animals, nature

Approved

  • The music pass with 22 synth sounds #564
  • Birds at night; a real owl as random one-shots every 20–45 s #380
  • Small random pitch on frequent sounds; a test that bans two sounds sharing one id #605

Rejected

  • Crickets (annoying), synth wind and synth owls #380
  • Odd first picks: a finger snap for cash, a 6 s rocket for unlock, a sword slash for escape #564
  • Sounds for Rare and Secret drops: they stay silent #381
Test silently

A hidden Studio still plays through the speakers. Right after starting a playtest, set every Sound and SoundGroup volume to 0 and keep doing it for new ones. Check audio by logging which sounds were created and played.

08

Verifying in the real game

Tests prove logic; only the engine proves how it looks and feels. Every visible change gets at least one layer from the engine side.

LayerWhat it provesWhen
Lune tests and boot testLogic, saves, that the game startsEvery commit
Static layout and render checkUI fits at six sizes; part and triangle budgetsEvery PR
Hidden Studio over MCPScreenshots, collisions, labels, timings, a 2-player testEvery visible change
Cloud Luau ExecutionBehaviour on a real server: terrain probe, smoke testBefore publish
Human reviewLooks right, feels right, reads rightBefore merge
Players and analyticsWhether it helps the funnelAfter release

Tips

  • Screenshots leave out BillboardGuis. Read label sizes with execute_luau (AbsoluteSize, WorldToViewportPoint).
  • Measure, then state the number: "label shows at 54 studs, hidden at 66" #615.
  • Walk a dummy into props from four sides to find invisible walls.
  • Drive input with Studio-only attributes, never the real mouse.
  • The PR body lists exact checks and results, and says plainly what was not tested.

Where AI is weak

Plan human time for these. They are where most second rounds came from.

Weak spotWhyWhat helps
Taste and simplicityThe AI adds options, text and featuresMockups with options; "fewer words" rules in the kit
HearingIt can't listenMeasure and log; the human picks by ear
Organic shapesPrimitives read as stubby limbsMetaballs, surfaces of revolution, or report the limit
Colours in RobloxOffline renders don't match Roblox lightLift darks; check in Studio
Phone feelIt never holds a phoneLayout gate at phone sizes; a human on a real device
Axes and orientationBlender and Roblox axes differCheck in Studio, not on the sheet
Fun and balanceIt can't feel pacingPacing sim with bot players; funnel data

New game checklist

Proposed

A one-page list a bot follows on day one of a new game, so the second game starts where Steal a Slime ended instead of where it began.

Repo and gates

  • Folder under games/, its own CLAUDE.md
  • Tests, lint, typecheck, place safety and layout gate wired in from the first commit
  • Budgets file for parts, triangles, instances

Look

  • Theme sheet and palette picked from renders
  • The kit (chapter 03) before the first screen
  • Style guide decided with Merijn

Shared code

  • Saves, inventory, rate limits, analytics from shared/luau
  • What is new and game-agnostic goes back to shared

Safety

  • Memory DataStore mode and test hooks guard
  • Upload and publish dry-run by default

Economy and data

Proposed

How we balance before players see it, and how we decide what to build next after they do.

Pacing sim

  • Bot players on the real game code: casual, grinder, thief, victim
  • Before/after tables, as in the economy rework #561

Analytics

  • Server-only events, stable step names
  • Onboarding and shop funnels

Planning rule

  • At least 7 days or 1,000 players of data
  • Fix the biggest drop first; "a competitor has it" is not a reason

Release

Proposed

From merge to live, with the gates and who presses which button.

Pipeline

  • Merge, cloud tests, Studio report, Saved upload, smoke check, Published
  • Only the newest fully gated build goes out

Release checks

  • The 12:00 and 19:00 check with Merijn
  • Terrain probe and rollback plan

Release notes

  • Player-facing wording, reviewed like any UI text

Decision log

Proposed

One line per decision Merijn or Niels made, with the PR, so bots stop proposing what was already rejected.

Examples already made

  • New-player shield added then removed #402 #411
  • StreamingEnabled not merged: small gain for the risk #560

Why it matters

  • Many removals say what changed but not why; the log keeps the why
