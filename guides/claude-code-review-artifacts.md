# Generating review artifacts with Claude Code (Markdown only)

Team rule (`/workspace/team/RULES.md` #7): deliverables are **generated by Claude Code itself**, not
hand-written. Output format is **Markdown only** — no HTML.

## Recipe

1. Write the prompt to a file (e.g. `prompt.txt`). Include the target output path and an explicit
   read-only constraint: "Do not modify anything under `<repo>`; only write `/workspace/reviews/<name>.md`."
2. Run from `/workspace` with the wrapper `~/.local/bin/cc` (non-interactive, `-p`), in the background
   with a timeout and a log file. Long runs take 15–25 min:

```bash
cd /workspace
timeout 40m cc -p "$(cat prompt.txt)" \
  --add-dir <repo> --add-dir /workspace/reviews \
  --permission-mode acceptEdits \
  --allowedTools "Read" "Glob" "Grep" "Write" "Edit" \
    "Bash(rg:*)" "Bash(wc:*)" "Bash(ls:*)" "Bash(find:*)" "Bash(grep:*)" \
  > /workspace/reviews/<name>.log 2>&1 &
```

3. Verify afterwards (see checklist below).

## Pitfalls

- **Writes silently refused.** A rule like `Write(/path)` is *not* matched for file writes; only
  `Edit(path)` rules are, and even `Edit(path)` alone without `--permission-mode acceptEdits` got the
  write refused in `-p` mode. cc then finishes the analysis but writes nothing. Use plain `"Write"`
  `"Edit"` plus `acceptEdits` as above, and **always check the output file exists**.
- **No access outside cwd.** Without `--add-dir`, cc cannot read paths outside `/workspace`. Add every
  source repo and the output directory.
- **Read-only isn't enforced by the tool list alone.** State it in the prompt, then confirm with
  `git status` on each source repo.

## Validating mermaid diagrams

Extract each ```` ```mermaid ```` block and render it with mermaid-cli (Node 22 via nvm):

```bash
source ~/.nvm/nvm.sh && nvm use 22
echo '{"args":["--no-sandbox"]}' > /tmp/puppeteer.json
mkdir -p /tmp/mmd
awk '/^```mermaid/{f=1;n++;next} /^```/{f=0} f{print > ("/tmp/mmd/d" n ".mmd")}' \
  /workspace/reviews/<name>.md
for f in /tmp/mmd/*.mmd; do
  npx -y @mermaid-js/mermaid-cli -p /tmp/puppeteer.json -i "$f" -o "${f%.mmd}.svg" || echo "FAIL $f"
done
```

If a diagram fails, **ask cc to fix it** (new `cc -p` run quoting the error) — do not hand-edit.

## Regenerating

Keep the previous version with a suffix before regenerating, e.g.
`mv review.md review.handwritten.md`, so nothing is lost.

## Checklist after each run

- [ ] Output `.md` exists and is non-empty (`ls -l`, `wc -l`); no `.html` produced
- [ ] Log shows no permission refusals
- [ ] `git status` clean on every source repo
- [ ] All mermaid blocks render
- [ ] No other files modified

## PR reviews (rule 6)

Work in one directory per review, e.g. `/workspace/reviews/<repo><n>/` (see `mnlib27/`): `meta.txt`
(head SHA + PR body), `pr.diff`, `checks.txt`, `comments.txt`, a checkout in `repo/`, cc's `review.md`,
`body.md` and `cc.log`. Older single-file reviews: `pr18-review.md`, `pr32-review.md` (+ `.log`).

- Pin the head SHA in the prompt and in the review title ("PR #18 review: `jolt/tz-hardening` @ 3a147491").
- cc (strongest model) reads the full diff plus related code: correctness, security, tests (against
  `/guides/testing-guidelines.md`), design. It should run things where it can and put the evidence in the
  review (commands, results, scratch dir), and say what it could not run.
- Output: verdict first (`**Verdict: APPROVE | COMMENT | REQUEST_CHANGES**`), then body, then inline
  comments as `path:line` + text. For a re-review, a new file (`pr18-rereview.md`, `pr18-rereview2.md`).

### Posting as the bot

Check the findings before posting (rule 6). Post as your own App, never as Merijn: Phoenix uses
`~/.local/bin/ghbot-phoenix` (`gh` with the phoenix-bot-mxndarijn App token). Build a payload
(see `pr42-payload.json`) and post one review with all inline comments:

```json
{ "commit_id": "<head sha>", "event": "REQUEST_CHANGES",
  "body": "**Verdict: REQUEST_CHANGES** (Claude Code review, head 25fca9a1)\n\n...",
  "comments": [ { "path": "scripts/x.sh", "line": 42, "side": "RIGHT", "body": "..." } ] }
```

```bash
ghbot-phoenix api -X POST repos/<o>/<r>/pulls/<n>/reviews --input payload.json
```

One review with inline comments is quieter than many separate comments (see `github-notifications.md`).
Thread replies and conversation comments: see `pr-watch.md`. Bots may post reviews and replies without
asking (rule 9); they never merge.

## Evidence and screenshots

- Keep evidence next to the review, e.g. `/workspace/reviews/navigator2/`: `in-your-own-words.md`
  (goal, finish condition, evidence, constraints), `summary.md`, `measurements.md` from a re-runnable
  script (`measure_edit.py`), `tests-before.txt` / `tests-after.txt`, `smoke-*.txt`, and
  `before-*.png` / `after-*.png` of the same scenario taken from the real app (Qt: `QWidget.grab()`, offscreen).
- **Images in PRs on private repos:** push the PNGs to a separate orphan branch that is never merged, and
  link them pinned to the commit SHA:

  ```bash
  git worktree add --detach /tmp/shots && cd /tmp/shots
  git switch --orphan phoenix/screenshots-<topic>
  cp /workspace/reviews/<dir>/*.png . && git add . && git commit -m "Screenshots for PR #<n> (<what>), not for merge"
  git push origin phoenix/screenshots-<topic>     # as the bot (credential helper ghapp-token-<bot>)
  ```

  Link: `![tree mode](https://github.com/<o>/<r>/raw/<full-commit-sha>/<path>.png)`. Example (private
  Navigator2, PR #2): branch `phoenix/screenshots-raw-toggle`, commit `a6b8854`, links
  `https://github.com/Mxndarijn/Navigator2/raw/a6b8854ba1e058c1fdfbc1cfca1e9e093b82e767/switch/2-raw-mode.png`.
  Pinning to the SHA keeps old links working when you add a new commit for a later round.
- Never put tokens or secrets in reviews, logs or screenshots.
