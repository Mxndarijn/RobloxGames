One obby for every server, one board for everyone

Every server already builds the same course from the clock. This page proposes how to name that course, keep one fastest-time board across all servers, keep it cheat-proof and cheap, and what changes in the obby rules. No game code changes yet.

What exists today

  • Course is already the same everywhere. slot = floor(serverTime / ROTATION_SECONDS), and ObbyCourse.pick(slot) + build give the same 6 sections on every server and client. The server publishes only the slot (OBBY_SLOT); each client builds its own copy.
  • Timing is already server-side. ObbyService starts the clock at the portal and stops it on the finish pad. A skipped section or a finish under MIN_RUN_SECONDS (19 s) marks the run invalid.
  • The best time is runtime only. session.obbyBest = { slot, seconds }. A rejoin forgets it. Nobody else sees it.
  • Entry rule (2026-11-01). You can't enter a course you already cleared. Your base lock counts down 50% slower while you run.
  • Boards today. Five Hall of Fame boards on OrderedDataStores, refreshed every 60 s, with a "Show me on leaderboards" setting that hides you as "Hidden player". Memory mode ranks only this server.

So the "shared ID" is already there: it is the slot. What's missing is a safe key, a shared store, and the rule changes.

1. Course ID

The board key has two parts: which 30 minutes (the slot) and which course content (a hash).

PartWhatWhy
Slotfloor(serverTime / 1800)Same on every server. GetServerTimeNow is synced across servers.
Content hash8 hex chars of a hash over the built course: every part's size, position, rotation, look and motion, rounded to 0.01, plus OBBY.COURSE_VERSIONDuring a rolling update, old and new servers can build a different course for the same slot. A different hash means a different board, so times never mix.
Board nameObby_<slot>_<hash>One board per course and code version.
RecommendedHash the built course, not just the picks

A hash of picks alone misses a tweak inside a section's code. Hashing the build output catches every change by itself. COURSE_VERSION stays as a manual "reset the board" switch. The server builds the course once per rotation already, so the hash is computed once per 30 minutes (pure: ObbyCourse.hash(course), Lune spec checks two builds of a slot match).

What players see: a short course number on the portal sign and the board: "Course #1,204". It counts from the first slot of the release (OBBY.COURSE_EPOCH), so it starts small instead of "#996,432". The hash is never shown to players; it goes in a server warn and in the admin menu for debugging.

2. Where the board lives

Recommended: AMemoryStore SortedMap, one per course
  • Entry: key = userId, sort key = ms × 10⁵ + seconds into the course (lower wins; equal times go to whoever set it first), value = { ms, name, hidden }.
  • Write: one UpdateAsync when a counted finish beats your own best on this course. It keeps the lower time, so two servers can't overwrite each other. Retry 3 times with backoff.
  • Read: each server reads the top 100 every 30 s. That's ~200 units a minute per server, about 25% of an 8-player server's share. The top 10 goes on the board; the rest gives "your rank" down to #100, deeper shows "#100+". (Request-unit costs per the docs today: re-check before building.)
  • Expiry: course end + 1 hour. Long enough for "Last course" on the board. Then it's gone: nothing to clean up.
Memory mode and tests (house rule 4)

The board store follows the Persistence pattern. At boot it picks the backend:

  • DataStoreMode = "Memory", Studio, or GetSortedMap fails → an in-memory sorted map that ranks this server only (like the Hall of Fame boards in memory mode).
  • Otherwise the real MemoryStore. Status goes on a workspace attribute ObbyBoardStatus (Ok / Memory / Error) with a warn on each bad change.
  • MemoryStore isn't a DataStore, but a cloud script on the real place would still write the live board. So cloud scripts and tests get the memory store too, through the same DataStoreMode switch.
  • The store is passed in through ctx. Lune specs run two fake "servers" on one shared memory store to prove cross-server ranking, ties and hash separation.

Shared code first (house rule 10). A "best value per period, across servers" board has nothing game-specific in it. The pure core goes to shared/luau/src/ranking/PeriodBoard.luau (keys, sort keys, keep-the-best, rows, ranks, memory store) with a thin MemoryStoreBoard adapter, next to OrderedBoard. The game keeps only the obby rules.

Permanent record: optional, not in v1. See question 4.

3. When a time counts

The client never sends a time. The server posts only when all of these hold:

#Must be trueExists today?
1The run started at this server's portal, on this course's slot, and the clock is server time from entry to the finish tick.Yes
2Every section was passed, in order (run.section); none was skipped.Yes (invalid)
3Time ≥ MIN_RUN_SECONDS (19 s).Yes
4The finish is within the course's 30 min + REBUILD_GRACE (90 s). It posts to the run's own slot.Partly: add the check
5No anti-cheat flag during the run (the movement guard's teleport or speed flags, or a server move outside the known fall resets).New: read the flag
6The server's course hash is the board's hash (true by construction: it writes to its own board).New
7The session can save (not read-only, not a Studio fallback profile) and the store is the live one.New
8It beats the player's own best on this course. At most one write per finish.New

Times are measured at the server's 0.1 s tick, so the board shows tenths: "0:42.3".

Not covered on purpose

A truly fast but legit route is fine. We don't add a per-course "too fast" floor yet: there's no data. Instead ObbyNewBest logs every top-10 time, and after a week we look for outliers. Each board expires after an hour, so a cheated time can spoil one course at most.

REBUILD_GRACE90 sUnchanged
Why the boost stays on its timer

Today a course lasts 10 minutes and the boost cycle is 10 minutes (5 on, 5 cooldown), so an active runner gets about 50% boost uptime. "Once per course" with 30-minute courses drops that to 5 of 30 minutes, about 17%. That's a big income cut nobody asked for. Keeping the timer keeps the economy exactly as it is. No pacing-sim run needed.

Why the lock perk needs a limit

The entry rule from 2026-11-01 was "a perk for running, without farming the same course". With retries, a player could loop one course for 30 minutes and keep their base lock at half speed the whole time. Giving the 50% only until your first counted finish keeps the perk for real runs and stops the loop. The run card shows the "50% slower" chip only while it applies.

7. Edge cases

CaseWhat happens
Server shuts down mid-courseTimes already posted stay (they live in MemoryStore). A run in progress is lost, like today. Nothing to flush on close.
Join at minute 29You can still enter. A finish within the 90 s grace counts for that course. The sign shows the countdown, so nobody is surprised.
Rejoin or server hopYour best on this course comes back from the board on the next read. Hopping gives no advantage: same course, same board.
TiesSame tenth of a second: whoever set it first ranks higher.
MemoryStore downThe board keeps its last rows with "Board offline". Runs still count for the boost; your best is kept in the session and posted on your next finish.
Cheater gets a time inThe board expires an hour after the course. Later: an admin "remove time" action (needs its own guard, since TestHooks is memory-only).
NamesThe display name is saved in the entry when the time is posted, so every server shows the same name without lookups. Display names are moderated by Roblox, the same as on the Hall of Fame boards. Players type no free text.
"Show me on leaderboards" offShown as "Hidden player"; the userId never goes to clients (same as Leaderboard.fromPage). Changing the setting updates your entry on the current course.
PrivacyStored: userId (server only), display name, time, hidden flag. Deleted automatically an hour after the course ends.
AvatarsR15 runners are already set to the standard scale. R6 is left alone today; R6 hitboxes differ a little. Watch top-10 data before acting.
Speed Coil, PvP slows on runnersBoth change times. See question 3.

Open questions for Merijn

1. Boost x1.5 with retries
  1. On its own timer, as today (any counted finish when it's ready). Same income as now. Recommended.
  2. Only on your first clear of each course. Uptime drops from ~50% to ~17%.
2. Lock 50% slower
  1. Only until your first counted finish on this course; retries run the lock at normal speed. Recommended.
  2. On every run, retries too. Simple, but you can loop the course to keep your base locked longer.
3. Speed Coil and PvP slows during a run
  1. Off during a run: everyone runs at the same speed, so times are fair. Recommended.
  2. Allowed: the coil is part of the game, but bought speed buys board spots.
4. A permanent record
  1. None in v1: only the live course board. Recommended.
  2. A "Courses cleared" board in the Hall of Fame (count, uses the existing board code).
  3. "Obby wins" (times in the top 3), later: needs one server to settle each course.
5. Course number on the sign
  1. Short, counting from release: "Course #1,204". Recommended.
  2. No number, just "new course in 12:34".
